店舗エージェント向け LLM 中継仕様書

1. 目的

親サイトで設定した利用者のLLM APIキーを店舗に渡さず、親サイト内に表示した店舗ページで、店舗自身のエージェントと会話・予約できるようにする。

利用者は親サイトで複数店舗を比較し、選んだ店舗のページで詳しい相談を続ける。店舗エージェントは店舗側の機能を使い、利用者が内容を確認したうえで予約を確定する。

公式ランタイムを変更せずに中継する実装を行い、Chromiumでプロバイダー応答を置き換えた結合テストを実施した。実プロバイダー・他ブラウザ・規格への完全適合は未検証とする。検証済みの範囲と残る制約は11節に記す。

2. 基本方針
- 親サイトで、利用者がLLMルーター・モデル・APIキーを設定する。
- 選択した店舗サイトを親サイト内のiframeで表示する。
- 店舗ページ内で店舗のランタイムとエージェントを動かす。
- 店舗ランタイムのLLMリクエストを、店舗のService Workerと親子間メッセージ通信で親へ中継する。
- 親が利用者のキーでLLMを呼び出し、応答を店舗ランタイムへ返す。
- 店舗エージェントは、店舗ページに登録された機能を使って相談・予約を進める。
- 予約などの書き込み操作は、実行前に利用者が内容を確認する。
- 本物のLLM APIキーは店舗ページ・Service Worker・店舗サーバーへ渡さない。
利用者
  ↓
親サイト（LLM設定・APIキー保持）
  ├─ 店舗の比較・選択
  └─ iframe：店舗サイト
       ├─ 店舗チャット／店舗エージェント
       ├─ 店舗の予約機能
       └─ 店舗Service Worker
             ↓ LLMリクエストのみ中継
       店舗ページ ⇄ 親ページ → LLMルーター
3. 画面と利用フロー

3.1 親サイトで店舗を探す
1. 利用者は親サイトで日時、人数、予算などを伝える。
2. 親のAIが登録店のAIで空席・メニューを確認し、回答文の後に比較カードを表示する。
3. 利用者が店舗を選び、「お店を開く」を押す。
4. 親サイト内に店舗ページをiframeで表示する。
5. 店舗表示中は親の検索画面を隠し、「お店探しに戻る」だけのヘッダーと店舗ページを表示する。予約条件があるカードには「予約ページへ」も表示し、店舗とは別の予約ページを表示する。店舗と共通のデザインの通常フォームからAIなしで予約でき、「AIで予約する」を押すとチャットを開く。子の「AIに相談」を押すと親のAI設定で中継を開始する。AIのON/OFFや追加の許可カードは表示しない。
3.2 店舗ページで相談・予約する
1. 利用者はiframe内の店舗チャットに質問する。
   店舗ページの「AIに相談」でチャット専用の全画面を開き、「元の画面に戻る」で元の店舗ページへ戻る。親からの予約条件はチャット内に表示し、「反映」を押すと条件をユーザーメッセージとして投稿する。エージェント一覧は表示しない。LLM設定は「AIの設定」のモーダルで行い、親の中継を使う場合は店舗側の設定ボタンを表示しない。
2. 店舗エージェントは自店舗の情報や店舗側の機能を使って回答する。
3. 必要に応じて空席や料金を確認し、予約内容を提案する。
4. 予約確定などの操作では、店舗ランタイムが確認画面を表示する。
5. 利用者が確認した場合にのみ店舗側の処理を実行し、結果を店舗ページに表示する。
親は店舗のLLM呼び出しを中継するが、店舗に代わって予約処理を実行しない。

3.3 店舗サイトを直接訪れた場合

店舗ページには、親のお店さがしサイトへの誘導ボタンを表示しない。
店舗を直接開いた場合は、店舗アシスタントを利用し、チャット内で予約を完結する。予約ページには通常フォームも表示し、AIなしでも予約を完了できる。LLM中継は、親サイトから店舗をiframeで開いた場合に利用する。

4. 中継方式

4.1 店舗ランタイム
- LLMの接続先を、店舗オリジン内の中継専用URLに設定する。
- 例：`https://shop.example/llm-bridge/v1`。
- 公式ランタイムが送る /chat/completions リクエストをService Workerで受け取る。
- 実際のAPIキーを店舗側の設定に入れない。
公式ランタイムは空のキーおよび demo を拒否するため、起動オプション `router`・`byokKey`・`model` に、店舗内の中継先・`relay-<session>` 識別値・親が選んだモデルを渡す。この識別値は利用許可の証明として信用せず、親側で接続元・セッション・利用者の許可を別途検証する。

4.2 Service Worker
- 中継専用URLへのリクエストだけを対象にする。
- リクエストを受け取り、対応する店舗ページを介して親へ送る。
- 親からの応答を、ランタイムが読めるHTTPレスポンスとして返す。
- 親と接続できない場合、タイムアウト・エラーを返す。別の外部宛先へ黙って転送しない。
- Workerが対象ページを制御していることを確認してから、店舗チャットを有効にする。
- Service Workerは一時セッション終了後も残り得るため、接続終了後は中継を停止し、新しい許可なしに再利用しない。
4.3 親子間の通信
- 店舗ページと親ページは postMessage などを使って通信する。
- 親は、許可された店舗オリジンと、そのiframeの送信元ウィンドウを検証する。
- 店舗は、許可された親オリジンと送信元を検証する。
- 送信先オリジンは明示し、任意の相手へ送らない。
- 接続確立時にセッションを識別し、リクエストIDで応答と対応付ける。
- 中継可能な操作、モデル、回数・時間・費用の上限を設ける。具体的な上限値は検証後に決める。
- 接続解除・親画面の終了・権限取り消し時は、店舗からの新規リクエストを拒否する。
4.4 LLMリクエストと応答
- 親は、利用者が選んだLLMルーターに、利用者のキーを付けて問い合わせる。
- 店舗側が送るメッセージ、モデル指定、ツール定義などを、親が許可した範囲で中継する。
- 公式ランタイムはストリーミング応答を読むため、回答の断片とツール呼び出しを含む応答を、期待される形式で店舗側へ返す。
- エラー、タイムアウト、中断も店舗側へ伝える。
- 店舗側が指定した任意のURLへ、親のキーを付けて送らない。送信先は親で選択されたLLMルーターに限定する。
5. 予約と確認
- 空席照会は予約確定ではない。
- 店舗エージェントは店舗側で登録された操作を呼ぶ。
- 予約・変更・キャンセルなどの書き込み操作の前に、店舗ランタイムが操作先と内容を表示し、利用者の確認を得る。
- 店舗側は確定直前に空席、日時、人数、金額、利用時間、キャンセル条件を再検証する。
- 確認後に条件が変わった場合は、変更内容を表示し再確認する。
- 二重予約を防ぐため、予約試行を識別して重複送信に対応する。
- 送信後の通信断などで結果が不明な場合は、失敗と断定せず、店舗側で結果を確認する。
- 予約確定の成否は店舗からの結果に基づいて表示する。
予約確定は公式ランタイムの `onActionConfirm` フックから店舗の確認ダイアログを表示する。拒否時に予約されず、承認時にだけ店舗へ予約を送信することを結合テストで確認した。フォームの入力操作は確認なしで実行されるため、全書き込み操作で確認するという規格上の要求には未対応である。

6. プライバシーと安全性
- 本物のAPIキーは親のブラウザ内に保持し、選択したLLMルーター以外に送らない。
- 店舗から親には、LLM処理に必要な会話・ツール定義などが送られる。利用者にその旨を示す。
- 親から店舗には、LLMの応答と処理に必要なエラー情報のみを返す。
- APIキーをURL、ログ、トレース、店舗へのメッセージに含めない。
- 店舗の指示やツール定義は外部入力として扱い、親の接続先・利用上限・安全上の制約を変更させない。
- 店舗ページが悪用された場合に備え、許可した店舗・セッション単位で中継を制限し、利用者が停止できるようにする。
- iframeの埋め込みは許可した親サイトに限定する。
- 店舗内リンクで記事・追加ページへ遷移しても、同じ登録親から表示できる。APIと管理画面は埋め込めない。古い予約リンクは店舗と共通のデザインの予約ページへ案内する。
7. エラー時の動作
- 親にLLM設定がない：親で設定を案内し、完了後に店舗へ戻る。
- 接続許可がない・拒否された：店舗チャットを開始せず、その理由と手動操作の導線を表示する。
- Service Workerが未準備・利用不可：中継を開始せず、再試行または通常の店舗ページ利用を案内する。
- 親との接続が切れた：新規のAIリクエストを停止し、再接続を案内する。入力中の内容は可能な範囲で保持する。
- LLMや店舗の機能が失敗した：失敗を表示し、成功したように扱わない。
- iframeを表示できない：店舗ページを別タブで開く導線を出す。ただし、別タブでは本中継が自動的に使えるとはみなさない。
8. 検証順序

段階1：LLM中継の実証
1. 1店舗をiframeで表示する。
2. Service Workerの制御開始を確認する。
3. 公式ランタイムの接続先と中継用識別値を設定する。
4. 親のAPIキーでLLMを呼び、文章を店舗チャットに表示する。
5. 店舗側のネットワーク通信・ログ・保存領域に本物のキーがないことを確認する。
段階2：ツール呼び出しと予約
1. 店舗エージェントから空席照会を行う。
2. ツール呼び出しを含むストリーミング応答が正しく往復することを確認する。
3. デモ予約を提案し、利用者の確認後にのみ店舗側の予約処理が実行されることを確認する。
4. 確認拒否、接続切断、タイムアウト、二重送信を試す。
段階3：複数店舗とブラウザ
- 店舗を切り替えた際、前の店舗の接続権限が残らないこと。
- 親サイトの一覧・比較結果から店舗を開く場合と、`?shop=<slug>` で指定する場合の双方を試すこと。
- 対象のPC・スマートフォンのブラウザで、iframe、Service Worker、ストリーミングの動作を確認すること。
9. 残る検証事項
- 実際のLLMプロバイダーを使った接続、課金、ツール呼び出しの確認。
- Safari・Firefox・実機スマートフォンでのiframe・Service Worker・ストリーミングの互換性。
- 中継方式がOpen Agentic Webの該当仕様に適合するか。特にユーザーの選択・同意、ルーターの扱い、認証情報の分離を検証する。
- 金額での費用上限。現在は40回・30分のセッション上限と、1呼び出し120秒の制限を親で管理する。
10. 受け入れ条件
- 利用者が親で一度設定したキーで、iframe内の店舗チャットを使える。
- 店舗ランタイムは、店舗自身の情報・機能を使って回答できる。
- 予約は利用者の確認後にのみ店舗側で実行される。
- 本物のキーが店舗ページ・店舗Service Worker・店舗サーバーに渡らない。
- 許可されていない店舗、切断済みセッション、上限超過のリクエストは拒否される。
- 中継に失敗した場合、予約や問い合わせが成功したように表示されない。
- 親サイトの一覧・比較結果から該当店舗を開ける。
参考：公式ランタイムのLLMクライアント／Open Agentic Web MVP仕様

11. 実装と検証の記録（2026-11-14）

- 店舗側：`agentic/site/llm-relay.js` と `llm-relay-sw.js`。Workerが対象ページを制御してから接続を要求する。中継対象は店舗内の `agent/llm-bridge/v1/chat/completions`（POST）と `models`（GET）だけで、接続がない場合はエラーにする。Workerはヘッダー受信後も含め125秒で終了する。
- 親側：別リポジトリ `gemihub-agent` の `site/shop-frame.js` と `site/llm-relay.js`。許可したiframeのウィンドウとオリジン、セッションを検証する。店舗を開くたびに新しいiframeへ置き換え、古いページからの通知を受け付けない。
- Chromiumで、回答とカードの表示順、店舗トップ・予約ページの選択、子の操作によるAI開始、条件の反映、MCPによる店舗情報取得、ツール呼び出しを含むストリーミング、予約確定の拒否と承認、中継停止後の拒否、複数店舗の切り替え、390px幅での表示、埋め込み拒否時の別タブ案内を確認した。
- 結合テストのプロバイダー応答は固定データで置き換える。14回のモデル呼び出しを親がキー付きで行い、店舗への通信、店舗のlocalStorage・sessionStorage・Cookieにそのキーがないことを確認した。実プロバイダーへの通信・課金を検証した結果ではない。
- 店舗の自動テストで、送信元とセッションの検証、途中切断、ヘッダー受信後のタイムアウト、二重予約防止、Service Workerの許可範囲、静的トップページと予約ページに親への誘導ボタンがないことを検証する。実行手順は `docs/restaurant-agent.md` に記載する。
- 金額による上限、規格の完全適合は未対応・未検証として残る。

## 会員登録不要と予約なしの店舗

飲食店の予約は氏名と電話番号で受け付け、会員登録・ログインを要求しない。メールアドレスは受け取らず、お客様へメールも送らない。予約の通知はお店（`notificationEmail` と店主）だけに届く。`seating.confirmationCall`（既定 true）のときはお店が電話で折り返して確認する。false（人気店）のときは折り返さず、予約時刻から5分（`lateReleaseMinutes`）を過ぎても来店がなければ他のお客様を案内する。どちらの扱いかは予約フォーム・確認ダイアログ・予約完了表示・お店への通知メールに表示する。席の自動解放は行わない。ログインがないため、予約の作成は1つの接続元から1店舗につき1時間に10件まで（超えると 429）、1つの電話番号が1店舗に持てるこれからの予約は3件まで（超えると 409）とする。同じ予約の再送はこの数に含めない。公開ページには会員向けの登録・ログイン・マイページ・会員限定問い合わせの導線を表示しない。管理画面の認証は維持する。

店舗設定 `reservationsEnabled: false` では情報のみ公開する。席設定・予約メニューは公開条件にせず、予約ページ・予約の導線・予約エージェントを公開しない。直接の予約APIも受け付けない。未指定は既存どおり予約あり。
