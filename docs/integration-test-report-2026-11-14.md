### キーの扱いと検証上の制限

画面の「Save and start」は、公式ランタイムのローカル用BYOKプロファイルCookieも保存する。実キーを店舗へ送らないため、テストではそのCookieだけをブラウザのHTTP通信から除外し、通常のアプリケーションCookieは保持した。キーの保存・ページ再読み込み・条件復元のアプリ処理は変更していない。

1回目の再検証では、残席確認用の補助APIRequestContextがブラウザのCookie監視を通らなかったため、その実行をキー送信防止の証拠には含めない。最終確認では「Save and start」後のプロファイルCookieを明示的に削除し、以降の残席確認も監視対象のブラウザfetchへ統一した。適用済みのタブ設定とローカルのプロファイルは維持した。

したがって、今回の成功は条件保持と予約経路の回帰確認であり、通常のローカルブラウザでCookie保護なしに操作した場合のキー非送信を保証するものではない。これは店側の条件保持修正とは別の、公式ランタイムの既知の制約。

### モデルの回答文に誤記・多言語の混入がある

既定のOtariモデルの回答文には、コース名の誤記や多言語の混入があった。空席・満席の比較や予約操作は確認できたが、デモに向けたモデル・指示の品質調整は未完了。

表示箇所として確認できたのは、親の比較カードと親チャット。11/20の比較記録では、親カードの `courseName` が「パーティープレラン」となっており、シード定義の「パーティープラン」と異なる。親チャットにも「관련」などの混入がある。

### 生のAPI応答による原因の切り分け

追加診断では、親を経由せず灯の予約ページで、冬の炉端コースの名前・材料・アレルゲン・厨房の注意書きを日本語で説明するよう依頼した。情報確認だけと指定し、テスト側でも予約・書き込みPOSTを禁止した。Otariへのモデル要求は5回で、予約・書き込み要求は発生しなかった。

HTTPレスポンスのSSE本文をランタイムとは独立に復元し、エージェントの返却テキストと照合した。

| 段階 | 観測結果 |
| --- | --- |
| Otari応答4：`menu_allergen_checker` | 生の `delta.content` に「countryside対応」「безопасное allocation quality control」などが既に含まれる |
| 窓口への次の入力 | 専門エージェントの崩れた返答が、ツール結果としてそのまま渡されている |
| Otari応答5：`reservation_front` | 最終応答の生テキストに「予約前先-neededに」が含まれる |
| ランタイム内の応答 | 応答4・5とも、SSEを独立に復元して表示用の構造を解析した結果と全文一致 |

**直接の原因は、Otariが `alibaba/qwen3.8-flash` の応答として返す生成テキストの崩れ。CSS・フォント・Markdown描画によって外国語が追加されたものではない。店のネットワーク単体でも再現し、親の比較処理だけに閉じた問題でもない。**

比較カードのコース名についても、初回の記録では描画前の `courseName` 自体が誤っていた。親はモデルが生成した `courseName` を文字列として検証し、`textContent` で表示している。コースIDから正式名を決定して照合する仕組みがないため、誤記された文字列も型・長さの検証を通る（`site/finder.js`、`site/site-actions.js`、`site/script.js`）。

一方、モデル自体の生成特性なのか、Otari内部の推論・変換設定に起因するのかは、このAPI側からの観測では判定できない。`temperature` などの比較や、別モデル・別ルーターとの比較は未実施で、それらを根本原因と断定していない。
