# 仕様見直しメモ（2026-11-14）

対象: [飲食店予約エージェント仕様 v0.3](../specs/restaurant-spec.md)。仕様の見直しと、その後の実装反映の状況を記録する。

## 見直しの根拠

- [提供された公式ルール本文](../specs/rule.md)と[応募要項](https://cognizant-agenticweb.devpost.com/)を照合した。ルール §4 の準拠対象は応募期間開始時点の技術規格であり、随時更新されるmainへの追随を応募上の必須条件にしない。
- 応募開始は2026-11-11 20:00 PST＝2026-11-12 04:00 UTC＝同日13:00 JST（ルール §1）。開始前に公開済みの参照版は[e4a8727](https://github.com/cognizant-ai-labs/agentic-web/blob/e4a8727d5c6807233b8976f28494bbdac7bc1c6e/docs/worldwide_agentic_web_mvp_spec.md)。MVP Profile 0.2（2026-11-06）の本文は、実装が採用する63a956c時点と全文一致し、Git blob SHAはどちらも`7a09be795cc3eee47f601f1a6bc7dc26d408f7a9`だった。ランタイムの採用版と規格の準拠版は区別する。
- 規格 §3.2 は外部接続前の同意を求める一方、利用者が明示的に選ぶ別の同意方針・UIを認める。店ごとのカードや同じ宛先への毎回の確認を製品要件にする必要はない。
- BYOK、特定モデル、CRUSE、公式ランタイムの画面構成は、規格が一律に要求するものではない。本作では利用者の希望によりBYOKと初回の設定モーダルを残す。
- 別オリジン連携は本作の中心として残す。相互運用デモでも規格 §6 の確認対象になる。
- Devpostからの取得は403だったが、利用者が`specs/rule.md`に置いた本文で確認できたため、「ルール全文は未確認」という状態は解消した。本人の参加資格や権利保有を確認済みとするものではなく、今回、規約への同意や提出操作は行っていない。提供されたルール本文自体は変更していない。

## ルール本文で補足・修正したこと

- ルール §4 に基づき、英語または英訳の提出資料、審査終了までの無償・制限のない試用、既存プロジェクトの期間内の主要更新の説明、第三者API・OSS等の利用条件を仕様へ追記した。
- 審査終了は2027-01-18 17:00 PST＝2027-01-19 10:00 JST、提出締切は2027-01-11 08:00 PST＝2027-01-12 01:00 JST（§1）。
- BYOKは禁止されておらず、キー設定UIも任意とされる。ただし現状の「自分のAPIキーを入れて試す」手順だけで無償試用の条件を満たすとは断定しない。通常利用のBYOKと審査用アクセスを分けて設計し、試用手順は未決の実装・提出準備事項とする。
- Otariの利用は任意。利用時のメール等は応募ページの追加提出項目であり、特定プロバイダーを使う義務にはしない。
- 2分未満の動画はルール本文では`should`。公開YouTubeへのアップロードと、無許可の第三者素材を使わないことは`must`。提出時は本文の強さを区別する。
- 提供された本文には、全ソースの公開や特定のLLM・ランタイムの使用を必須にする記載はない。公開ネットワーク等の必須ファイルと、利用するOSSのライセンス条件は残す。
- 審査4項目の均等配点は §6 に明記されている。機能追加の理由にはせず、審査対策を製品仕様へ戻さない。

## 残すもの

- チャットで条件を聞き、登録店を探して店のページで内容を見て、希望すれば予約する機能。
- 親が持つ店名・ジャンル・エリア・URL。基本情報での絞り込みに店の問い合わせを使わない。
- 指定済みの条件で候補が15店以上ある場合だけ、未指定のジャンル・場所を聞く。14店以下なら追加質問しない。「おまかせ」「指定なし」は絞り込みなしとして受け付け、5店以上は4店ずつ確認する。
- 初回のAI設定、外部接続前の同意、予約確定前の内容確認、秘密の分離、根拠のある回答、失敗と結果不明の報告。
- 店側の席数・メニュー管理、空席判定、予約確定、同時予約時の超過防止。

## 必須仕様から外したもの

- 独立した条件入力・比較欄、活動一覧、専用比較カードの形式、入力フォームの強制。
- カードと回答文の表の重複。カードがあれば文章は短い次の操作案内だけにし、`/buttons`のようなコマンドを案内しない。
- 「この店で予約へ」というボタン名。「この店を見てみる」にして、まず詳細を見る操作とする。
- 店ごとの同意カードと初回の接続説明。ジャンル・場所で候補を絞り、件数を示して「問い合わせますか？」と一度聞く操作に置き換える。
- ページ移動だけの追加確認ダイアログ。予約確定や外部への書き込みに必要な確認は残す。
- 店舗数・店名・データ・モデル・利用時間・人数境界の固定。
- CSVなどの付加機能、詳細なAPI・データ型・画面配置の指定、ホスティング案、動画台本、審査対策、日程表、タスク分割。

外した項目は削除を強制する機能ではなく、実装を続けるための必須条件から外したもの。既存の保護対象や予約の整合性は維持する。

## 現行実装との差分

| 項目 | 現行 | 見直し後 |
| --- | --- | --- |
| 相談と結果 | 条件・比較カードはチャット内 | 維持。カード形式の固定は不要 |
| 回答の重複 | 指示で抑制しているが、カードに加えて同じ表や`/buttons`が返ったという報告あり | 情報は一か所だけ。カードがあれば文章は短い案内にする |
| 店を選ぶボタン | この店を見てみるに変更済み | 予約するかは店ページで決める |
| 親の基本情報 | 店名・料理・正しいエリア・URLを保持し、ジャンルと場所で絞り込み可能 | 維持 |
| ジャンル・場所の質問 | 候補15店以上のときだけ未指定の希望を質問。14店以下は追加質問なし | 維持。両方指定なしでも全登録店を候補にする |
| 問い合わせの確認 | 絞り込んだ店数を示し「問い合わせる」か「条件を変える」を選ぶ。店ごとのカードは廃止 | 維持。別の初回説明や許可操作は追加しない |
| 店への移動 | `irreversible`操作として追加ダイアログ | 単なるページ移動に追加確認を必須にしない |
| 店側の予約確定 | 内容確認を行う | 維持 |

回答重複の抑制は指示に反映したが、実モデルの誤回答を完全に防いだとは扱わない。ページ移動の追加確認は今後の実装対象。公式ランタイムの可逆な`write`が即実行される既知の挙動についても、規格上の実行前提示を自動的に満たしたとは扱わない。

親の登録店は現在3店。店側のデモデータと照合して新宿・渋谷・横浜に修正し、中華・イタリアン・和食で絞り込めるようにした。
