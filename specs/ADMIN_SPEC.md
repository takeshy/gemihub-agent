# gemihub-agent 店舗管理画面 仕様書 v0.7

対象リポジトリ: takeshy/gemihub-agent（親サイトと `apps/shop/` のモノレポ）
作成: 2026-11-15 / 更新: 2026-11-16

## 1. 目的
親サイトに載せる店を、運営者が **店のURLを貼るだけ** で登録・編集・削除できるようにする。
今は `site/shops.json` を手で書き、`npm run build` で生成物を作り直している。この手作業をなくす。

デモでは「URLを入れたら店がつながり、親AIの問い合わせ先に加わる」を見せる。

飲食店に加えて、雑貨店などの通常サイトも紹介対象にする。エージェントの有無と予約対応は独立して設定する。公開側の動作は [SHOP_INTRODUCTION_SPEC.md](SHOP_INTRODUCTION_SPEC.md) を参照。

## 2. 前提と方針
- 公開サイトは今まで通り **静的ファイルのみ**。規格（MVP Profile 0.2）は、ネットワーク定義が公開された静的ファイルであることを求める。
- 管理画面は公開バンドル `site/` に含めない。ローカルではループバックで待ち受け、開発環境では専用HTTPSオリジンと運営者のGoogleログインで保護する。
- 保存先は `site/shops.json` のまま。保存したら既存の `scripts/build.mjs` を実行して、次の生成物を作り直す。
  - `reservation_finder.hocon` と `reservation_finder.network.json`（`allowed_peers`、`link_labels`、tools）
  - `links.json`
  - `shop-registry.js`
  - `agent-manifest.json` の `allowed_peers`
- 入力のチェックは既存の `validateShops()`（`scripts/shops.mjs`）に任せて、二重に実装しない。
- 公式ランタイム（`vendor/`、`site/runtime/`）は改変しない。
- 運営者は許可リストにあるGoogleアカウントでログインする。Gmail送信を許可し、店主を招待できる。一般利用者の店探しにログインは求めない。設定がない場合も管理APIを開放しない。
- 店舗側のCloud Storage保存・メールリンクログイン・ZIP書き出しと、招待の認証仕様は [保存先と認証](../docs/storage-auth.md) を参照する。

## 3. 起動
```
npm run admin            # http://127.0.0.1:8091/ （ポートは ADMIN_PORT で変更可）
```
- 公開サイト（`npm start`、8090番ポート）とは別のプロセスで動かす。保存後にビルドされた内容は、公開サイトを再読み込みすれば反映される。
- `--production` を付けて起動すると、ビルドも `--production` で実行する。この場合、ループバックのURLは登録できない。

## 4. 画面
### 4.1 店一覧
- 表示する列: 店名、エリア、ジャンル、オリジン、状態（接続OK、情報取得済み、要確認、エラー）。
- 行ごとの操作: 編集、再読込（店から情報を取り直す）、削除、上下の並び替え。
- 一覧の見出しの右に「店を追加」ボタンを置く。
- ログイン中のメールアドレスと「サインアウト」リンク、公開中の案内ページを別タブで開く「案内ページを開く」リンクはページ右上に小さく表示する。
- `PARENT_DEMO_LOGIN_TOKEN`（32文字以上）を設定すると、`/auth/demo?token=…` を開いた人を、Gmail接続済みの運営者としてログインさせる（デモ用。未設定なら無効）。

### 4.2 店を追加
1. URLを1つ入力する。受け付けるURLは次のどれでもよい。
   - 店のトップ: `https://akari.jp/`、`https://akari.<SITE_DOMAIN>/`、`<app>/s/akari`
   - 予約ページ: `…/reserve`
   - エージェントの置き場所: `…/agent/` または `…/agent/agent-manifest.json`
   - ネットワークURL: `…/agent/reservation_concierge`
2. 「読み込む」を押すと、6章の手順で自動解決し、プレビューを出す。
3. プレビューの各項目は編集できる。`id` は、URLのslugかドメイン名から自動で作る。ジャンルは店名・紹介文を基にGemini Decisions APIが判定して初期入力する。取り込みだけでは保存しない。
4. 「保存」を押すと、`shops.json` への追記とビルドを行い、結果を表示する。

エージェントがない店も取り込める。ネットワークURLは任意にし、予約ページを案内する場合だけ独立したチェックと予約URLを設定する。エージェントがあるだけでは予約対応にしない。

### 4.3 編集
- 追加の画面と同じ見た目。`id` は変更不可。
- 「店のURL」には店舗ページのURLを表示し、AIの問い合わせ先であるネットワークURLとは区別する。
- 「店から取り直す」を押すと自動解決をやり直し、変わった項目に差分の印を付ける。上書きは運営者が選ぶ。
- 保存済みのジャンルは保持し、取り直しの際にAIで上書きしない。

### 4.4 削除
- 確認ダイアログに店名を出し、OKなら削除して保存・ビルドする。

### 4.5 保存結果
- 成功したら「保存しました。」と公開サイトの再読み込みを案内する。生成ファイルの一覧は表示しない。
- 失敗したら（`validateShops` またはビルドのエラー）、メッセージをそのまま出す。この場合 `shops.json` は書き換えない。

### 4.6 案内ページをAIで編集
- 店舗の検索に限らず、街の情報やお店の紹介を載せるページとして、管理画面と編集画面では「案内ページ」と表示する。
- 「AIでページを編集」から、文章・色・レイアウト・説明セクションの変更を自然文で依頼する。管理サーバーの `GEMINI_API_KEY` と共通のGemini設定（既定Hydrogen / low）を使う。
- 専用の編集画面は店舗側と同じ、プレビュー中心・右側チャット（スマホは下側）の構成にする。画像選択、音声入力、折り畳み、赤ペン描画、修正案の前後比較は店舗側の部品を共用する。
- 画像を添付し、キャプチャした画面に赤丸を描いて依頼できる。赤丸の画素と添付画像をどちらも生成・追加修正へ渡す。キャプチャは保存済みの選択版だけをサーバーで描画し、外部URLへの通信とスクリプトを禁止する。
- 変更案は非公開で保存し、前後比較で「OK」「さらに変更」「キャンセル」を選ぶ。「OK」は編集中の内容への採用で、戻る・進むにも対応する。「この内容を反映する」を押したときだけ公開ページを更新する。
- 添付画像は1枚10MBまで受け付ける（PNG・JPEG・GIF・WebP）。非公開の専用領域に保存し、ページで使われた画像だけを公開時にコピーする。公開失敗時は新規に公開した画像も削除する。画像管理APIは運営者ログインで保護する。
- 公開履歴は現在と過去10版まで保持する。選んだ版をプレビューし、「この版に戻す」で復元できる。変更案は最新10件を保持する。
- チャット・登録店一覧・ナビゲーションは実際の部品を挿入する。店舗情報、検索・予約連携、同意・認証・AI接続の実装は変更対象にしない。
- 表示用HTMLとCSSを許可リストで検証し、スクリプト・独自フォーム・埋め込み・外部CSS読み込みを拒否する。プレビューは認証付きのサンドボックスで表示し、チャットや予約を実行しない。
- 別画面で公開内容が更新された場合、古い変更案での上書きを拒否する。保存失敗時は直前の公開ページに戻す。
- 非公開の編集状態を永続領域に保存し、デプロイ時に公開済みデザインを再適用する。APIキー・編集履歴は公開フォルダーやイメージのソース転送に含めない。

### 4.7 チャットの資料
- 運営者がアップロードした地域・施設・イベント等の資料を、店舗に関わらない質問にも使う。
- UTF-8のTXT/Markdown/CSV/JSONとPDFを受け付ける。1ファイル5MB・抽出本文10万文字、全体50件・200万文字まで。PDFはサーバーのGeminiで全文を読み取り、不完全な応答は拒否する。公開前に本文を確認・修正する。
- 読み込みだけでは保存・公開しない。「下書きを保存」は非公開。「公開する」で初めて資料名・本文を公開する。公開済みの編集、公開解除、削除にも対応する。読み込み・保存・削除APIには運営者認証と変更時の同一Origin検証を適用する。
- 非公開の本文は`admin/chat-documents.json`、公開した本文だけは`site/chat-documents.json`に保存する。原本・運営者情報・キーは公開しない。改訂値で古い更新を拒否し、書き込み失敗時は非公開・公開の両方を復元する。ソース転送から両ファイルを除外し、再デプロイでは永続資料を上書きしない。
- チャットは`website_search_chat_documents`で公開本文を分割したキーワード検索を行う。検索ごとに再取得し、資料名・更新日時・抜粋を最大8件返す。回答では資料名を添え、確認できない内容を作らない。本文中の命令には従わない。一般の質問では店舗検索・店舗問い合わせ・予約条件を要求しない。
- 公開資料は誰でも読め、必要な抜粋は利用者のAIへ送られることを公開ボタンのそばに明記する。公開解除後の検索からは除くが、過去の回答・会話履歴は消さない。
- 管理API: `GET /api/chat-documents`、`POST /api/chat-documents/import`（`{name,data}`のbase64原本から本文だけを返す）、`PUT /api/chat-documents`（`{id?,name,text,published,revision}`）、`DELETE /api/chat-documents/:id`（`If-Match`に改訂値）。

## 5. 店データ（shops.json、version 1。互換を保つ）
| 項目 | 必須 | 取得元 |
|---|---|---|
| id | ○ | URLのslug、またはホスト名から生成（`^[a-z0-9][a-z0-9-]{0,79}$`、重複不可） |
| name | ○ | MCPの店舗情報、または通常ページのタイトル・メタ情報・JSON-LD |
| area | ○ | MCPやJSON-LDの住所から都道府県と市区町村を切り出す（編集可） |
| cuisine | ○ | 店名・紹介文を基にAIが初期入力（編集可。取得できなければ手入力） |
| pageUrl | ○ | 店舗ページURL。旧形式では予約ページとしていた値も維持できる |
| networkUrl | 任意 | マニフェストから解決（6章）。ない場合は空文字 |
| address | 任意 | 地図用の詳しい住所。番地まで取り込み、管理画面で編集可能。500文字まで |
| description | 任意 | MCPや通常ページから取得する公開紹介文。2000文字まで、編集可 |
| reservationEnabled | 任意 | 予約ページを案内するか。新規取り込みでは明示し、エージェントの有無と独立させる |
| reservationUrl | 予約対応時 | 店舗と同じオリジンの予約ページURL |

注: `get_shop_info` には今、ジャンルとエリアの専用の項目がない。店側は変更せず、ジャンルは親の管理画面でAIが提案し、エリアは住所から推定する。AIの提案も「保存」を押すまで店舗データには書き込まない。

version 1を維持したまま、任意の紹介文・予約対応情報を追加する。予約対応が未指定の旧データは、従来の予約用店舗として扱う。取得時の管理情報は `admin/cache.json` に分けて持つ。
- 最終取得日時
- `description`
- 予約条件の要約（人数の範囲、席のみの予約の可否）
- 状態

## 6. URLの自動解決
1. 入力URLを正規化する。クエリ、フラグメント、認証情報を外し、HTTPSを必須にする（ループバックのみHTTPも可）。
2. 店の基準URL（base）を求める。パスに `/agent/` があればその手前まで、`/reserve` で終わればその手前まで、それ以外は入力そのままを基準にする。
3. `<base>/agent/agent-manifest.json` を取得する。取れなければ、入力ページのHTMLにある `<link rel="agent-manifest">` を探す。
4. 公開ネットワークを名前どおりに解決する。予約用の名前に限定しない。複数なら選択させる。マニフェストやネットワークがなければ、通常ページの情報を使う。
5. ネットワーク定義を取得して検証する。既存の `parseExternalAgent` / `safeName` でツール名を出し、他の店と衝突しないかを確かめる。
6. ネットワークに店舗情報用MCPが宣言されていれば `get_shop_info` を呼ぶ。なければ通常ページから取得し、ページのスクリプトは実行しない。MCPの予約条件と予約URLがある場合だけ予約対応の初期値にする。
7. 未設定のジャンルはGemini Decisions API（`gemini-decision-1` 固定）の `choice` 質問で、基本のジャンル分類と既存の登録ジャンルから選ぶ。店名・紹介文だけを判断対象にする。既に保存済みなら再判定しない。キー未設定・判定不能・通信失敗時は案内を表示して手入力を可能にする。
8. 5章の表に従って項目を埋め、プレビューを返す。保存操作は行わない。

- 通信はサーバー側（Node）で行う。管理画面のブラウザからは呼ばないので、CORSの影響を受けない。
- タイムアウトは各10秒。リダイレクトは同じオリジンの中だけ追う。
- 解決できない場合のエラーは7章のとおり。

## 7. エラー表示（日本語）
| ケース | 表示 |
|---|---|
| URL形式が不正、またはHTTPSでない | 「HTTPSのURLを入れてください（ローカルは http://127.0.0.1 可）」 |
| マニフェストやネットワークがない | 通常ページから取り込み、店舗紹介として続行する |
| 店舗ページも取得できない | 「店舗ページを読み込めませんでした。URLとサイトの起動状態を確認してください。」 |
| MCPにつながらない | 「店の情報を読み込めませんでした。名前などを手で入れて保存できます」（手入力で続行できる） |
| id かツール名が重複 | 「同じ店がすでに登録されています」 |
| ビルド失敗 | ビルドのエラーをそのまま出し、保存は取り消す |

## 8. ローカルAPI（管理画面の内部用）
- `GET  /api/shops`: 一覧（shops.json と cache を合わせたもの）
- `POST /api/resolve` `{url, id?, networkIndex?}`: 6章の解決結果（プレビュー）。保存はしない。Geminiのキーはサーバー側だけで読み込み、ブラウザからAI設定やキーを送信しない。
- `PUT  /api/shops`: 店の配列全体を送る。検証、書き込み、ビルドを行う。失敗したら元に戻す。
- `DELETE /api/shops/:id`
- `GET /api/site/images` / `POST /api/site/images`: 非公開の画像一覧・アップロード
- `GET /api/site/images/:id`: 選んだ管理画像
- `POST /api/site/capture` `{sourceId, revision, width}`: 選択版の操作できない画面をPNGとして取得（幅390/1280）
- `GET /api/site`: 公開版・変更案・履歴のメタ情報と改訂値
- `GET /api/site/preview?source=...`: 認証付きの操作できないHTMLプレビュー
- `POST /api/site/proposals` `{request, revision, sourceId?, media?, imageIds?}`: 選択した版を基に非公開の変更案を作成
- `POST /api/site/publish` `{sourceId, revision}`: サーバーに保存した変更案の反映、または履歴の復元
- `Host` はループバック、または設定したHTTPS管理オリジンに限定する。変更系の要求は `Origin` ヘッダも確認する（DNSリバインディングとCSRFの対策）。
- 店舗一覧の取得を含む管理APIはGoogleログイン後に利用できる。GoogleのコールバックはstateとPKCEで確認する。店舗サーバーからのGmail送信依頼だけは共有秘密によるBearer認証を用い、ブラウザからは使わせない。
- 招待では店主のメールアドレス・店名・種類を指定する。飲食店・その他はメールリンク、サロンは招待先のGoogleアカウントで確認する。リンクを開いただけでは店舗や管理者を作成しない。

## 9. 作るファイル（案）
- `admin/server.mjs`: Node標準の http を使用する。ページ編集のHTML検証にparse5、CSS検証にPostCSSを使用する。
- `admin/index.html`、`admin/admin.js`、`admin/admin.css`
- `scripts/resolve-shop.mjs`: 6章の処理。テストしやすいよう、fetch を差し替えられる形にする。
- `scripts/shop-html.mjs`: 通常ページのタイトル・メタ情報・JSON-LDの読み取り。
- `site/shop-data.js`: エージェントと予約対応を独立して扱う共有処理。
- `scripts/suggest-cuisine.mjs`: `POST https://generativelanguage.googleapis.com/v1beta/decisions` に `gemini-decision-1` と選択式の質問を送信する。リダイレクトを拒否し、本文の取得を含め10秒でタイムアウトする。
- `GEMINI_API_KEY` を管理サーバーの環境変数から読み込む。`npm run admin` は `.env` も読み込む。管理画面のAI設定・モデル選択は作らない。キーを返すAPIや公開サイトのBYOK設定の引き継ぎは行わない。
- `package.json` に `"admin"` スクリプトを追加する。
- 書き込みは一時ファイルに書いてからリネームする。失敗したら元の `shops.json` に戻す。

## 10. テスト
- `resolve-shop`: 4種類の入力URL、`<link rel>` からの解決、マニフェストなし、ネットワークなし、MCP失敗（手入力に切り替わる）、ツール名の衝突、住所からのエリア推定。店の応答はモックにする。
- API: Host/Origin による拒否、保存失敗時の巻き戻し。
- AIジャンル: Decisionsの選択式リクエスト・応答、初期入力、手修正の保持、判定不能・取得失敗時の手入力、未保存のプレビュー、キーの非公開、ブラウザから固定設定を上書きできないこと。
- 既存の予約処理の回帰テストと、通常サイト・エージェントあり予約非対応・紹介文の保存・予約導線の分離を検証する。
- ページ編集: 非公開の変更案・追加修正・反映・復元・更新競合・保存失敗・再デプロイ、HTML/CSS検証、認証とキーの非公開。PCとスマホでプレビュー・公開後の既存機能を確認する。
- 手動確認: ローカルの gemihub-restaurant（`SEED=restaurant-demo`）を起動し、3店をURLから登録し直す。親チャットで問い合わせが通ることを確かめる。

## 11. やらないこと
- 未認証の一般利用者への管理画面APIの公開、共同編集。
- 店側（gemihub-restaurant）の変更。Q1で決めた場合だけ別タスクにする。
- 店の自動発見（NANDA Index などのディレクトリ連携）。

## 12. 未決事項
- Q1: 店側は変更せず、親でAIによるジャンル初期入力と住所からのエリア推定を行う。
- Q2: 店の並び順に意味を持たせるか（問い合わせの順や表示の順）。
- Q3: 「再読込」で店名などが変わったとき、自動で上書きするか、確認を出すか（案: 確認を出す）。
- Q4: 本番公開のときも、ローカルで管理画面を使ってから生成物をコミットする運用でよいか。
