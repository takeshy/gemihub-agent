# 飲食店予約エージェント仕様

- 版: v0.3（2026-11-14、仕様の簡素化・提供された公式ルールとの照合）
- 親サイト: `gemihub-agent`。店サイト: `gemihub-restaurant`。
- 目的: チャットで希望に合う登録店を探し、その店のページで内容を見て、希望すれば予約する。
- 本書は見直し後の仕様。現行実装との差分は [仕様見直しメモ](../docs/spec-review-2026-11-14.md) に記載する。

## 1. 規約・規格から残す要件

応募条件は提供された [公式ルール本文](rule.md) を基準とし、[応募ページ](https://cognizant-agenticweb.devpost.com/)を補足に使う。記載が食い違う場合は公式ルールを優先する（ルール §11）。技術要件は、ルール §4 が指定する応募期間開始時点（2026-11-12 13:00 JST）の [Worldwide Agentic Web MVP Profile 0.2](https://github.com/cognizant-ai-labs/agentic-web/blob/e4a8727d5c6807233b8976f28494bbdac7bc1c6e/docs/worldwide_agentic_web_mvp_spec.md) を参照する。以下は本作に関係する要点であり、原文の代わりではない。

### 1.1 応募時に必要なもの

- 動作する公開サイト、公開ネットワークJSON、ブラウザ実行用ランタイム、対話UI。
- 機能の説明文、スクリーンショット、ブラウザ実演と本人の説明を含む公開YouTube動画。動画は2分未満が目安。
- 提出資料は英語、または英訳を用意する。動画・説明文・試用手順なども対象（ルール §4）。
- 審査終了の2027-01-19 10:00 JSTまで、主催者・審査員が無償かつ制限なく試用できるアクセスを提供する（§1、§4）。BYOKの有無と別に、審査用の試用手順を用意する。
- 既存のgemihubを利用するため、応募期間開始後に行った主要な更新を説明する。第三者のAPI・データ・OSSの利用条件と権利を守る（§4）。
- Otariの利用は任意。使う場合は応募ページの追加項目として、アカウントのメールと利用上の問題・改善点を提出情報に含める。
- 提出締切は2027-01-12 01:00 JST（§1）。参加資格・権利条件は公式ルール本文で確認する。サイトの動作仕様に動画台本や審査対策は含めない。

### 1.2 技術上残すこと

| 要件 | 出典 |
| --- | --- |
| 宣言的なネットワークとmanifest、リンク情報を公開し、ブラウザで検証・実行する | 規格 §2、§3 |
| 公開時はHTTPS。別オリジンから読む公開ファイルにはCORSを設定する | §3.3–3.4 |
| サイト操作の入力を検証し、書き込み・取り消せない操作では実行前に宛先と引数を示す。確認はモデルでなくランタイムが扱う | §3.1、§5 |
| 外部接続前に宛先と目的を示して同意を得る。確認方法の緩和には利用者の明示的な選択が必要 | §3.2、§5 |
| 指定した店のネットワークを正確に読み、利用者側のブラウザ・選択中の推論設定で実行する | §3.2 |
| BYOKでは接続先・モデル・キーを選択または入力でき、保存した設定を削除できる。キーが必要で未設定なら推論を止める | §4 |
| キーをURL・プロンプト・ログ・店への要求に入れない。private contextは明示した例外以外、別ネットワークへ渡さない | §4–5 |
| 不正な定義、許可されない接続、循環、実行上限超過は止めて報告する。副作用の結果が不明なときは成功扱いや自動再実行をしない | §3、§5 |
| 実行状況を秘密を出さず確認できるようにする。開発用の詳細は折りたたんでよい | §5、SHOULD |

規格 §6 の相互運用確認では、2エージェントのネットワーク、内部呼び出し、根拠のあるMCPまたはサイト操作、承認後の別オリジン連携、キーとprivate contextの分離、異常時の停止を示す。

専用の比較カード、条件パネル、活動一覧、CRUSEフォーム、特定モデル、3店舗固定、店ごとに毎回押す同意カードは、規格の必須要件ではない。公式スキルやランタイムは実装手段であり、その画面構成を製品仕様として必須にしない。

## 2. 残す製品の範囲

### 2.1 親が持つ店の基本情報

親は登録店の基本情報を保持し、店へ問い合わせずに案内・絞り込みに使う。

| 情報 | 用途 |
| --- | --- |
| 店ID・正式な店名 | 店の識別、回答の表示 |
| 料理ジャンル | 中華、イタリアン、和食などの希望で絞る |
| エリア | 場所の希望で絞る |
| 店ページ・店ネットワークのURL | 店への問い合わせと詳細ページへの移動 |

編集元は現在の `shops.json` を使う。固定のジャンル一覧や店舗数は要求しない。「中華」に広東料理を含めるなど、登録情報に基づいて候補を選ぶ。一般の飲食店検索は行わず、登録外の店名やURLを作って案内しない。

空席や現在のメニュー・価格・材料は、親の基本情報だけで断定しない。必要な候補だけ店のエージェントに問い合わせる。

### 2.2 利用者が使う画面

- 相談、条件の確認、問い合わせ結果、店の選択はチャット内で完結させる。
- 初回はAI設定モーダルでプロバイダーを選び、APIキーを入力する。モデルと接続先は詳細設定で変更できる。設定済みなら直接チャットを開く。
- 店の情報は一か所にまとめる。カードに出した情報を、回答文の表や文章で繰り返さない。カードがあれば文章は「お店を選んでください」程度にする。
- 独立した比較欄や固定のカード形式は必須にしない。`/buttons`などのコマンドを案内せず、実際の画面上の操作で選べるようにする。
- 店ページへのボタン名は「この店を見てみる」。予約確定や予約開始と受け取られる表現にしない。
- 登録店の基本情報は親で参照できるようにする。独立した店一覧を常時大きく表示することまでは要求しない。

### 2.3 問い合わせ前の件数確認

初回に接続先や用途を説明する画面や、店ごとの許可カードは出さない。

- 指定済みのジャンルと場所で、親の基本情報から候補を絞る。候補が15店以上ある場合だけ、未指定の希望を一度聞く。14店以下なら追加質問しない。「指定なし」ならその条件では絞らず、両方とも指定なしなら全登録店を候補にする。
- 接続前に店数を計算し、「この条件だと○店に問い合わせます。問い合わせますか？」とチャットで一度だけ聞く。店数は問い合わせ先の目安であり、LLMの呼び出し回数ではない。
- 1回に確認するのは最大4店。全候補数と今回の店数を表示し、「確認する」で今回表示した店に問い合わせる。5店以上なら、結果を出して利用者の続行希望を待ち、次の最大4店を確認する。「条件を変える」なら接続しない。該当0店なら勝手に対象を広げない。
- 日時・人数・ジャンル・場所や対象店が変わったら、件数を再計算して確認する。過去の検索の確認を別の検索へ流用しない。

規格上の同意は、この対象店と件数を見て「確認する」を選ぶ操作で扱い、別の「許可」操作を追加しない。

## 3. チャットの流れ

1. 希望を読み、指定済みのジャンル・場所で候補数を調べる。15店以上ある場合だけ、未指定の希望を次のように一度聞く。

   > ジャンルや場所を絞ると、問い合わせるお店を減らせます。中華やイタリアンなどのジャンルや、新宿・横浜などの場所に希望はありますか？

   「おまかせ」「指定なし」でも進める。14店以下ならジャンル・場所は聞かない。すでに希望があれば聞き直さない。日時や人数も不足していれば、同じ返答でまとめて聞く。
2. 親の基本情報で候補を絞る。店の紹介だけなら、ここでチャットに回答する。
3. 空席を調べる場合に、日付・時刻・人数をそろえる。コースの要否、1人あたり予算、避けたい食材は任意。条件はチャットで変更できる。
4. 全候補数と今回確認する最大4店を先に伝え、一度聞く。利用者が進める操作をしたら、その候補店に問い合わせる。続きは次の発話で希望された場合に確認する。名前・連絡先・キー・相談用メモは渡さない。
5. 店の回答をチャット内で伝える。確認できた情報だけを使い、未確認・満席・問い合わせ拒否を区別する。材料の記載がないことを安全の保証にしない。条件・店名・価格を別の表で重複表示しない。
6. 「この店を見てみる」で、その店のページへ条件を引き継いで移動する。詳細を見てから予約するか決められるようにし、移動だけの追加確認ダイアログは必須にしない。
7. 利用者が予約を希望したら、店のページで引き継いだ条件を使い、必要なコース・代表者名・連絡先を補う。予約内容を表示して利用者が確認した後、店側で予約を確定する。

条件変更後の古い回答から予約を進めない。予約条件だけを店へ引き継ぎ、キーや連絡先をURLへ入れない。店ページでAIの設定が未保存なら、そのページで設定する。

## 4. 店側の最小機能

- 店が、予約に使える席数、営業・受付時間、席のみ予約の可否、メニュー・コースと価格・材料を管理できる。
- 予約人数と時間帯に基づいて空席を判定し、同時に予約が入っても席数を超えて確定しない。
- 親から読み取り専用で空席・メニューを調べられ、予約の確定は店のページで行う。
- 席のみとコースありを同じ予約として扱う。通常予約と宴会を別機能にせず、人数や利用時間など必要な違いだけを店の設定で扱う。
- 予約が成立したか分かる受領を返す。失敗・結果不明を成功として見せない。

管理画面の配置、CSV出力、細かなデータ型、API名、アルゴリズム、固定の利用時間・人数境界は必須仕様にしない。

## 5. 最小限の確認

- 候補14店以下ではジャンル・場所を聞かず、15店以上のときだけ未指定の希望を聞く。指定なしでも登録店を確認でき、5店以上は4店ずつ進める。指定済みなら再質問せず、親の情報だけで候補を絞れる。
- 基本情報の案内だけでは店に接続しない。件数を示して利用者が進めるまで接続せず、開始後は店ごとの確認が出ない。
- 結果と選択操作がチャット内の一か所に出て、カードと回答文が重複しない。登録外の店や`/buttons`を案内しない。
- 「この店を見てみる」で詳細へ移動できる。条件変更と引き継ぎが正しく、古い条件で予約を進めない。
- 店ページで内容確認後に予約が成立し、残席に反映される。同時予約で超過しない。
- 公開環境で規格 §6 の相互運用確認を行う。テスト用応答による確認と実モデル・実サービスでの確認を区別する。

## 6. 作業範囲

- 作業対象は `gemihub-agent` と `gemihub-restaurant`。gemihub.net本番、テスト用アカウント、`takeshy/gemihub`、kakerattaには変更を加えない。既存のmainと`08c75b6`に関する2026-12-15までの保護指示を維持する。
- 決済、電話受付、カレンダー連携、サイト負担の推論は今回の範囲に含めない。
- 公開先、モデルの固定、3店の具体的なシード、動画の秒割り、審査への打ち出し、マイルストーン、エージェントごとのタスク分割は機能要件から外す。
- 実装・検証の進捗は仕様見直しメモとテストレポートに記録する。公開・提出は別作業とする。
